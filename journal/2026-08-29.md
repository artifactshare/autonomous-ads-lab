### Learnings

1. **harness agent は PR を作れない(#3)。** `pull-requests: write` を付けても、リポジトリ設定「Allow GitHub Actions to create and approve pull requests」が無効だと GITHUB_TOKEN は PR を作成できず、workflow の `permissions:` では上書きできない。**自己修正のループが設定ひとつで閉じていなかった。**修正自体は完成しているのにブランチ push で止まっており、手順3〜4が構造的に空回りする
2. **push 競合は実在する(#6)。** 仮説ではなく、この実行中に main が `34150e6` → `090dd74` に進んで私の push が拒否された。私は rebase で回復したが、daily/weekly には rebase もリトライも無いので、同じ状況では Experience DB 更新と journal が消える。3つの ops workflow は concurrency group を共有するが、**人間の push はその外側**
3. **workflow 保護が期待通り効いた。** 古い main から切ったブランチを push しようとしたら、`ci.yml` から budget-guard job を消す差分になるため GitHub が拒否。「GITHUB_TOKEN は workflow ファイルを変更できない」という予算ガードの前提が、実際に機能していることを意図せず確認できた
4. 自動実行の構造化ログが残らないと、次回の harness agent は journal と git 履歴からしか状況を復元できない。**監査可能性の設計が自動実行でだけ抜けていた**(#4)
5. **main は保護ブランチで、bot は直接 push できない(#7)。** このジャーナル自体が main に載せられず、ブランチ `harness/journal-2026-08-29` に退避している。`required_status_checks` が `test` を必須とし non-admin に強制されるため、admin であるオーナーのローカル push だけが通っていた。さらに daily/weekly/harness の commit は `[skip ci]` 付きなので `test` が起動せず、**必須チェックは原理的に満たせない**
6. **daily/weekly は Actions 上で一度も実行されていなかった。** 全19 run が CI、残り1つが今回の Harness Agent。journal と `data/` の既存コミットはすべてオーナーのローカル実行によるもので、**workflow の push ステップは一度も通っていない**。次の cron(22:00 UTC)で初めて走り、そこで #7 により失敗する見込み
7. #3 と #7 を合わせると、**harness agent には変更を main に届ける経路が一つも存在しない**。直接 push は保護で拒否、PR 経由は PR を作れない。今回は「ブランチを push して issue で報告する」ところが限界だった。自己修正ループを閉じるには、この2つの設定を先に解く必要がある
