### Learnings

- **ワークフローファイルを変更できない制約下では、衝突の「原因」ではなく「面」を削るのが有効**。本筋は weekly.yml の push 前の `git pull --rebase` だが GITHUB_TOKEN では触れない。代わりに衝突するファイル自体をgitから外す・マージ意味論を変える、という2方向でコード側から攻められた
- **「成功しているワークフロー実行」は成果が残っていることを意味しない**。weekly は毎回 exit 0 で、`gh run list` 上は success。PRがマージされたかまで追わないと、課金だけ発生して成果ゼロのループを見逃す。`weekly_stale` 警告は13日間鳴り続けていたが、cronスキップという誤った原因に紐づいていたため誰も掘らなかった
- 生成物をgitに置くと、並行ジョブがある環境では衝突源になる。`data/experience.db` が既にgitignoreされていたのに `data/living-report.html` が漏れていたのは、方針が明文化されず個別判断だったため
- `data/events/*.jsonl` の「実行ごとにユニークなファイル名」という設計は正しく、一度も衝突していない。append-onlyな状態をgitで共有するときの手本
